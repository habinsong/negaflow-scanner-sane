## 0. 이 문서를 쓰는 이유

이식 프로젝트에서 가장 비싼 실수는 **이미 한 번 시도해서 실패한 것을
"개선"이라고 생각하며 다시 하는 것**이다.

코드에는 결론만 남는다. `--gamma-correction`을 활성일 때만 보내는 코드를
보면 "왜 굳이?"라는 생각이 들고, 고치는 데 10분이면 된다. 그리고 그것이
정확히 2026-07-29에 있었던 일이다.

이 문서는 **왜 그 10분짜리 수정이 틀렸는지**를 남긴다.

각 항목은 이렇게 적는다:

```text
무슨 일이 있었나 → 근본 원인 → 지금의 규칙 → Windows에서 무엇을 뜻하는가
```

# 제1부 — 터진 것

## 1. epson2 감마: 실기 없이 하드웨어 동작을 바꿨다

**날짜**: 2026-07-29 · **커밋**: `82b7b32` → revert `7f950dc`

**무슨 일**

`--gamma-correction`을 옵션이 비활성일 때는 보내지 않는 코드를 보고,
"비활성이어도 보내면 선형 감마가 더 확실히 걸리지 않나"라고 판단해
활성 검사를 제거했다. 커밋했다. 그리고 되돌렸다.

**근본 원인**

SANE의 "비활성"을 **"지금은 꺼져 있지만 설정은 가능"** 으로 오해했다.
실제로는 `OPT_GAMMA_CORRECTION`이 `SANE_CAP_INACTIVE`가 되는 조건이
초기화 시 `!s->hw->cmd->set_gamma` 하나뿐이다. 즉 **"이 하드웨어에는
감마 명령이 존재하지 않는다"** 는 뜻이었다.

그 상태에서 옵션을 보내면 `scanimage`가
`"attempted to set inactive option"`으로 **스캔 전체를 실패시킨다.**
개선이 아니라 그 기기에서 스캔을 아예 못 하게 만드는 변경이었다.

**무엇이 이 실수를 가능하게 했나**

- 실기(해당 A/B 레벨 Epson)가 손에 없었다. 테스트가 통과했다 — 테스트에
  그 기기가 없었으니까.
- SANE 원본을 읽지 않고 옵션 이름의 의미만 보고 판단했다.

**지금의 규칙**

```text
하드웨어 동작을 바꾸는 플러그인 변경은
  ① sane-backends 원본 확인
  ② 실기 검증
둘 다 없이는 릴리스에 넣지 않는다.
```

**Windows 함의**

이 코드를 이식할 때 활성 검사 3종의 비대칭
([driver-option-reference](driver-option-reference.md) §8.3)을 보면
"일관성이 없다"고 느낄 것이다. **그 비대칭이 정답이다.** 리버트 이력을 코드 주석에
남긴다.

그리고 더 일반적으로: **이식은 개선의 기회가 아니다.** 개선 후보는
[product-invariants](../99-plan/product-invariants.md) I-20에 모으고
양 플랫폼에 함께 적용한다.

## 2. 스캔 노출 개선: 문헌을 나중에 읽었다

**날짜**: ~2026-07-26, 2026-07-27 확정 종결

**무슨 일**

슬라이드 필름 스캔이 어둡게 나오는 문제를 "스캔 시점 노출"로 고치려 했다.
`--scan-exposure-time`, `--brightness`, 멀티 노출 브래킷을 **전부 배선했다.**
정렬 동기화 버그도 찾아 고쳤다. 결과는 **전부 실패 또는 무효과**였다.

**근본 원인**

세 겹으로 틀렸다.

| 시도 | 왜 안 되는가 | 어디에 적혀 있었나 |
|---|---|---|
| `--scan-exposure-time` | genesys는 사용자용 exposure/gain 옵션을 노출하지 않는다. 노출은 캘리브레이션 중 내부 처리(LED exposure calibration)라 외부 훅이 없다 | `sane-genesys` manpage |
| `--brightness` / `--contrast` | **sane-backends 1.0.32에서 제거됨.** 애초에 하드웨어가 아니라 소프트웨어 후처리라, 걸렸어도 16-bit raw에서는 본체 슬라이더와 같은 곱셈 | 릴리스 노트 genesys 항목 |
| 멀티 노출 | 하드웨어가 노출 시간을 바꿀 수 있어야 성립. genesys는 그 제어를 노출하지 않으므로 = 멀티샘플링이고, 멀티샘플링은 DR을 늘리지 못한다 | SilverFast 문서가 명시 |

**전부 코드를 쓰기 전에 30분이면 읽을 수 있는 자료였다.**

**실측이 문헌과 정확히 일치했다** (2026-07-26, E100D 6컷):

```text
필요량        18% 미드까지 +1.27 ~ 1.45 스탑
가용 헤드룸   캘리브레이션 화이트까지 최대 ~0.7 스탑
```

노출 제어가 열려 있었더라도 **필요량의 절반만 얻고 밝은 컷은 클리핑**됐다.
즉 구현이 성공했어도 문제는 안 풀렸다.

**지금의 규칙**

```text
하드웨어 능력에 기대는 기능은 구현 전에 manpage + 릴리스 노트를 읽는다.
"옵션이 있는지"가 아니라 "그 옵션이 하드웨어를 건드리는지"를 확인한다.
그리고 필요량과 가용량을 먼저 수치로 비교한다.
```

`hasScanExposureOption`이 false로 떨어지는 것은 **정상 동작이다.**
버그로 오해하고 우회하지 말 것.

**Windows 함의**

이식 중에 `hardwareExposureTimes = [11000, 14000, 30000]`과 노출 병합 코드
전체를 보면 "대상 기기에서 안 쓰이는데 왜 있지?"라는 의문이 든다.
**옵션이 있는 기기에서는 정상 동작하는 기능이다.** 지우지 않는다.
동시에 **genesys에서 되살리려는 시도도 하지 않는다.**

```diff
+  word_list = (SANE_Word *) cs2_xmalloc (3 * sizeof (SANE_Word));

+  (SANE_Word *) cs3_xmalloc(3 *
```

3개 원소를 쓸 버퍼를 2개로 잡는다. upstream 커밋
`9bea1ee256c744098576acee98053e094b4a14a2`가 고친 버그다.

**근본 원인 이상으로 중요한 것**

이 버그는 **몇 년 동안 조용히 있었다.** macOS 26의 강화된 할당자가
즉시 크래시로 드러냈을 뿐이다. 관대한 할당자에서는 인접 힙을 1워드
덮어쓰고 지나간다.

**교훈은 버그 자체가 아니다**: 우리가 SANE를 **직접 빌드해야 하는
이유가 생겼다**는 것이다. 그래서 `Formula/sane-backends-negaflow.rb`가
있고, 별도 keg가 있고, 설치 경로가 두 갈래가 됐다.

**Windows 함의**

- **Windows 힙이 이걸 크래시로 드러낼지 조용히 넘길지는 할당자에 달렸다.**
  page heap을 켜면 잡히고, 기본 힙에서는 안 잡힐 수 있다.
- 조용히 넘어가는 것이 **더 나쁘다.** 디버깅 불가능한 간헐적 오동작이 된다.
- 어느 쪽이든 **패치된 SANE를 쓰는 것이 맞다**(D-06).
- 배포물마다 이 패치 적용 여부를 **명시한다.** "아마 들어갔을 것"이 없어야 한다.
- 개발 빌드에서 page heap / ASan을 켜고 한 번은 돌려본다.

## 4. IR 전략 4종 → 3종: 설계했다가 도달 불가로 남긴 것들

**날짜**: 2026-07-06 설계, 이후 축소

**무슨 일**

IR 획득을 capability 기반 4전략으로 설계했다.

```text
genesys    --source "Transparency Adapter Infrared"  별도 패스
coolscan3  --infrared=yes + --batch-count=2          프레임2 = IR GRAY
epson2     --mode Infrared                           커스텀 빌드만
pieusb     --clean-image=yes                         백엔드 내부 클린
```

**현재 코드에는 3종만 있고, 그중 1종은 도달 불가다.**

| 전략 | 현재 상태 | 왜 |
|---|---|---|
| `.separateSource` | 살아 있음 | 정상 |
| `.separateMode` | 살아 있음(커스텀 빌드 전용) | stock epson2는 `SANE_FRAME_IR`이 `#if 0` |
| coolscan3 batch-count | **제거됨** | `SANE_FRAME_RGBI` 한 프레임을 stock scanimage가 분리 못 함 |
| `.cleanImage` | **정의만 있고 도달 불가** | 별도 IR 파일이 없어 호스트 IR 계약과 불일치 |

coolscan3 경로는 `--batch-count=2`로 프레임 2를 IR로 받는 접근이었고,
**같은 프로세스 안에서 해야 한다**(두 번 실행하면 IR 캐시가 소실된다)는
제약까지 파악한 상태였다. 그럼에도 stock `scanimage`가 RGBI를 두 TIFF로
직렬화하지 못한다는 벽에서 멈췄다.

**지금의 규칙**

```text
IRStrategy.cleanImage 는 도달 불가 상태로 유지한다.
"구현이 있으니 연결하자"가 정확히 틀린 판단이다.
```

**Windows 함의**

이식자가 `.cleanImage` 분기를 보고 `resolveMedia`에 연결하고 싶어질 것이다.
연결하면 pieusb 사용자가 "IR 지원"으로 표시된 토글을 켜고, 별도 IR 파일이
없는 결과를 받고, 3단계 검증이 실패시킨다.

**그리고 더 중요한 사실**: 이 개발 환경의 genesys 빌드는 OpticFilm에서
IR을 노출하지 않는다. epson2/epkowa도 미노출. 즉 **IR 경로 전체가 실기
검증되지 않은 채로 이식된다.** 이 사실을 validation-matrix에 명시한다.

## 5. GPL 파생 코드: 커밋 히스토리까지 재작성해야 했다

**날짜**: 2026-07-23 (본체 negaflow 쪽 사건)

**무슨 일**

본체 negaflow(Apache-2.0)의 네거티브 반전 코드에 darktable
negadoctor(GPLv3) 파생 — 프리셋 상수 6종 + CPU/Metal 수식 + "그대로 고정"
주석 — 이 들어가 있었다.

수습 비용:

```text
전부 자체 모델(shoulder-print-response-v4)로 교체
유도 과정과 공개 출처를 별도 문서로 작성
파생이 도입된 커밋 이후 15개를 단일 클린 커밋으로 collapse
도달 가능 히스토리에서 파생 수식·상수 전부 제거 확인
```

**"코드를 지웠다"로 끝나지 않는다. 히스토리에 남아 있으면 배포된 것이다.**

**지금의 규칙**

```text
외부 GPL 구현의 상수·수식을 "그대로" 가져오지 않는다.
수치는 계약 앵커에서 유도하고 derivation-lock 테스트로 고정한다.
유사도 회피 난독화는 무의미하다 — "실제로 파생이 아니게" 만든다.
```

**Windows 함의**

이 플러그인은 GPL-2.0-or-later이므로 반대 방향의 위험은 낮다. 하지만:

- **본체(Apache-2.0)와의 경계가 이 프로젝트의 존재 이유다.**
  프로세스 분리 + JSON/NDJSON 통신이 aggregation을 성립시킨다.
- `libsane`을 링크하는 순간 그 경계의 성격이 바뀐다(D-17, I-11).
  `dumpbin /imports`에 sane이 없어야 한다 — **검증 가능한 불변식이다.**
- CI 게이트(`verify-provenance.py`, `verify-boundaries.sh`)를 Windows
  파이프라인에도 옮긴다. 사람의 주의력에 맡기면 다시 일어난다.

## 6. 측정 도메인 불일치: "50:50 랜덤"으로 보이던 것

**날짜**: 2026-07-16 (본체 사건, 그러나 플러그인 출력 계약과 직결)

**무슨 일**

필름 base 실측이 "때로는 맞고 때로는 하얗고 파랗게" 나왔다. 재현이
안 되니 "랜덤"으로 보였다.

**근본 원인**

샘플러가 **비색관리 컨텍스트**(입력 태그 무시, 저장 인코딩 직독)를 썼다.
ICC 태그된 sRGB 파일에서 base가 감마 도메인으로 부풀었다
(linear 0.3 → 0.58, 0.1 → 0.35). 소비 측은 linear로 읽었다.

**"랜덤"의 정체는 경로 분기였다**: 오염된 경로가 성공하느냐, 정상 폴백이
걸리느냐가 캐시 상태에 따라 갈렸다.

**무프로파일 스캐너 raw(linear 태그)만 우연히 일치해서 직접 스캔은
정상이었다.** 즉 **이 플러그인의 출력만 정상이었다** — 버그를 가장 오래
숨긴 것이 우리 쪽 출력이 옳았다는 사실이다.

**지금의 규칙**

```text
비색관리 직독을 소비 도메인이 명확한 측정에 쓰지 않는다.
측정과 소비의 색 도메인을 명시적으로 일치시킨다.
```

**Windows 함의**

이 플러그인은 **태그 없는 16-bit linear TIFF**를 낸다. 본체가 그걸
linear로 재해석하는 계약이 이 사건 이후 명문화됐다.

- 이식 중에 출력 TIFF에 ICC 프로파일을 **넣지 않는다.** "친절하게"
  sRGB 태그를 붙이면 본체가 감마 도메인으로 읽고 색이 무너진다.
- `--gamma-correction` 선형 설정(§8 of driver-option-reference)이
  이 계약의 하드웨어 쪽 절반이다. 두 개가 한 세트다.
- 자세한 계약: [host-pipeline-contract](host-pipeline-contract.md)

## 7. 로컬 테스트가 CI를 재현하지 못했다

**무슨 일**

로컬 `swift test`는 통과하는데 CI가 실패했다. 테스트 코드도 strict
concurrency로 컴파일되는데 로컬 기본 설정이 그렇지 않았기 때문이다.

**지금의 규칙**

```text
푸시 전 CI와 같은 플래그로 검사한다 (scripts/ci/check-swift-concurrency.sh)
```

**Windows 함의**

같은 함정이 이름만 바꿔 나타난다.

| macOS | Windows 대응 |
|---|---|
| strict concurrency 플래그 | `/W4 /WX`, ASan/UBSan 빌드 |
| 로컬 debug vs CI release | FP 모델 플래그(`/fp:precise`, `-ffp-contract=off`) |

**FP 플래그가 특히 위험하다.** 로컬에서 수치 동등성이 통과하고 릴리스
빌드에서 깨지면 원인을 찾는 데 며칠이 든다. **빌드 플래그 자체를
테스트한다**(M4 통과 조건).

## 8. 테스트가 사용자 데이터를 오염시켰다

**무슨 일**

영속화 테스트가 실제 사용자 설정(UserDefaults)을 건드려, 릴리스 빌드에서
결정적으로 실패하고 iCloud 폴더까지 오염시켰다.

**지금의 규칙**

```text
영속화 경로는 테스트에서 임시 위치로 격리한다.
게이트를 두어 테스트가 사용자 데이터에 닿지 않게 한다.
```

**Windows 함의**

이 플러그인 테스트가 건드릴 수 있는 것:

```text
%LOCALAPPDATA%\Negaflow\Plugins\          설치 위치
SANE 설정 디렉터리                          dll.conf 등
%TEMP%                                     중간 파일
레지스트리                                  (현재 안 씀 — 계속 안 쓴다)
```

`SaneConfigTuner`가 macOS에서 공용 `dll.conf`를 **쓴다**. Windows에서는
D-05에 따라 no-op다 — **테스트 오염 위험이 구조적으로 사라지는 셈이고,
이건 우연한 이득이다.** 그 no-op를 "미구현"으로 오해해 나중에 구현하지 말 것.

## 9. 성능: 병렬화와 캐시 전치가 무효였다

**무슨 일**

본체의 자동 결함 검출이 15초 걸렸다. 병렬화했다. 캐시 전치도 했다.
**둘 다 실측상 무효였다.** 병목이 CPU가 아니라 **메모리 대역**이었다.

**지금의 규칙**

```text
최적화 전에 병목을 측정한다.
"병렬화하면 빨라지겠지"는 가설이지 결론이 아니다.
```

**Windows 함의**

노출 병합(`SANEBackend+ExposureMergingCore`)에 SIMD를 넣고 싶어질 것이다.
**D-11이 이미 금지한다** — 1차 구현은 스칼라, 수치 동등성 증명이 먼저다.

그리고 SIMD는 여기서 **정확성 문제**이기도 하다. 누적 합을 벡터 레인별로
나눠 마지막에 합치면 **다른 부동소수점 값**이 나온다. `downsampledError`,
`downsampledTexture`, `fullResLumaError`의 `total`이 전부 해당한다.

**누적 합은 스칼라로 남긴다.** 12패스 7200 dpi의 진짜 병목은 연산이 아니라
메모리다(M4의 타일 처리 항목).

## 9b. 문서가 "아마 이럴 것"을 사실로 적었다

**날짜**: 2026-08-04 (이식 문서 감사 중 발견)

**무슨 일**

`wire-contract`가 이렇게 적고 있었다.

> Swift `JSONEncoder`의 기본은 옵셔널이 nil이면 키를 생략하지 않고…
> 실제로는 `encodeIfPresent`를 쓰지 않는 합성 인코더는 `null`을 쓴다.

그리고 진행률 이벤트 예시에 15개 키를 `null`까지 전부 적어 두었다.
**둘 다 틀렸다.** 실제로 인코더를 돌려보니:

```json
{"devices":[{"driverVersion":"genesys (SANE)","displayName":"Plustek OpticFilm 8100",
"connectionType":"usb","id":"sane-genesys:libusb:001:002","vendor":"Plustek",
"model":"OpticFilm 8100","verifiedStatus":"compatibleTarget"}]}
```

- nil인 `usbVendorID`/`usbProductID`/`serialNumber`는 **키가 아예 없다**
- 키 순서가 **선언 순서도 알파벳 순도 아니다**(해시 순서)

**근본 원인**

Swift 합성 Codable은 옵셔널에 `encodeIfPresent`를 **쓴다.** 문서를 쓴
쪽이 그 반대로 기억했고, 문장에 "실제로는…"이라는 **주저의 흔적을
남긴 채로** 사실처럼 확정했다.

**무엇을 망가뜨렸을 뻔했나**

이 오류는 문서 안에 머물지 않는다.

```text
① Windows 구현이 모든 키를 null로 채운다 → macOS와 다른 JSON (I-5 위반)
② wire 골든을 바이트 비교로 설계한다      → 키 순서 때문에 매번 실패
```

②는 특히 나쁘다. 골든이 항상 빨간색이면 사람은 골든을 끄지, 원인을
찾지 않는다.

**지금의 규칙**

```text
런타임 동작에 대한 주장은 실행해서 확인한다.
"아마 이럴 것"을 적어야 한다면 그렇게 표시하고 spike로 만든다.
문장에 "실제로는", "…일 것이다"가 들어가 있으면 그건 미확인이다.
```

**Windows 함의**

같은 함정이 반대편에 있다. RapidJSON은 **쓰라는 대로 쓴다** — 선언 순서,
null 명시. 즉 Windows 구현의 "자연스러운" 출력이 macOS와 다르다.
**의식적으로 macOS 형태에 맞춰야 한다**
([wire-contract](../05-protocol/wire-contract.md) §4.2.2).

### 9b.1 측정 방법이 틀리면 숫자가 더 위험하다

같은 감사에서 두 번째 오류가 나왔다. 용어집에 "TPU를 쓰는 문서 20개"라고
적었는데 실제로는 **7개**였다.

원인: `grep -i tpu`가 **`output`에 걸렸다**(`ou-tpu-t`).

숫자는 서술보다 더 신뢰받는다. "약 20개 문서에서 쓰인다"는 검증 없이
통과하지만, 그 숫자가 틀리면 우선순위 판단이 통째로 틀어진다.

이 저장소 계열은 **이미 같은 함정을 밟은 적이 있다.** 본체의 IP 감사
기록이 부분 일치 오탐 목록을 따로 남기고 있다 —
`dimage`=`loadImage`, `lprof`=`legalProfiles`, `redscale`=`requiredScale`,
`impossible`=프랑스어 UI 문자열.

```text
grep 으로 센 숫자를 문서에 적기 전에 오탐을 확인한다.
확인할 수 없으면 숫자를 적지 않는다.
검증 불가능하고 계속 낡을 숫자라면 애초에 넣지 않는 것이 낫다.
```

그래서 용어집의 빈도 숫자는 **되돌리지 않고 삭제했다.** 고쳐 봐야
다음 편집에서 다시 낡고, `check-docs.py`가 검증할 수도 없다.

### 9b.2 검증 도구가 실제 빌드와 다른 플래그로 컴파일했다

2026-08-05, `imaging/align`을 붙이자마자 파리티가 깨졌다. 차이는 1 ULP였다.

```text
align.mix[third]        Swift 3ebbbbbb   C++ 3ebbbbbc
align.accum[zero].head  0번·2번 값만 1 ULP 차이
```

원인은 이식 코드가 아니었다. **파리티 스크립트의 컴파일 명령이었다.**

```bash
# CMakeLists.txt — 실제 빌드
add_compile_options(-ffp-contract=off)   # D-11

# tools/parity-check.sh — 검증 도구
c++ -std=c++20 -O2 ...                   # 플래그 없음
```

clang은 C++에서 `-ffp-contract=on`이 기본이라 `a + b * c`를 FMA 한 명령으로
축약한다. 중간 반올림이 사라져 **정확도는 올라가지만 결과가 달라진다.**
`mix()`의 `a + (b - a) * t`와 휘도 가중합 `r*0.2126 + g*0.7152 + b*0.0722`이
전부 여기 걸렸다.

이 간극은 **지금까지 드러날 수 없었다.** 그때까지 파리티 대상이 문자열
파싱과 정수 판정뿐이라 부동소수점 축약이 개입할 자리가 없었다.
`imaging/`이 처음으로 그 자리를 만들었다.

```text
검증 도구는 실제 빌드와 같은 플래그로 컴파일한다.
특히 부동소수점 관련 플래그는 "빌드 설정"이 아니라 계약의 일부다.
```

§7이 "CI와 같은 플래그로 로컬 검사한다"였다면, 이것은 그 반대 방향이다 —
**검사 도구 쪽이 실제 빌드보다 느슨했다.** 느슨한 쪽이 검사를 하고 있으면
통과는 아무것도 증명하지 않는다.

다행히 방향이 유리했다. 하네스가 더 느슨해서 **차이가 드러났다.** 반대로
하네스만 `-ffp-contract=off`이고 실제 빌드가 축약했다면 파리티는 통과하고
출하물만 달랐을 것이다. 운이 좋았던 것이지 설계가 막은 것이 아니다.

### 9b.3 이름이 하는 일과 코드가 하는 일이 달랐다

2026-08-05, `wire/request`를 옮기다 파리티가 세 줄을 뱉었다.

```text
req[pathDotDot]   Swift <ok>   C++ 거부
req[pathDot]      Swift <ok>   C++ 거부
req[pathDouble]   Swift <ok>   C++ 거부
```

**C++가 틀렸다.** macOS 원본이 이 셋을 통과시킨다.

원인은 이 문서가 아니라 [exact-option-contract](../02-frontend-contract/exact-option-contract.md)
§3.1의 서술이었다. macOS 코드를

```swift
URL(fileURLWithPath: outputPath).path == outputPath && isAbsolutePath
```

라고 인용해 놓고 "정규화 결과가 입력과 같고 `/`로 시작한다"고 해설했다.
`URL(fileURLWithPath:)`라는 이름과 "정규화"라는 말이 그렇게 읽히게 만든다.

실행해 보니 **후행 슬래시만** 없앤다.

```text
"/tmp/a/../../../etc/passwd"   →  그대로. 통과한다
```

이식자가 그 해설을 믿고 `..`을 거부하도록 짰고(그게 나다), 파리티가 잡았다.

두 가지가 겹쳤다.

```text
1. 문서가 API 이름에서 동작을 추론했다        →  §9b 와 같은 실수
2. 그 추론이 "안전한 쪽"이라 의심받지 않았다  →  더 위험하다
```

두 번째가 핵심이다. 틀린 추론이 **실제보다 안전한 동작을 서술**하면
아무도 의심하지 않는다. "경로 정규화 검사가 있다"는 문장은 읽는 사람에게
안심을 주고, 그래서 검증되지 않은 채 남는다.

```text
보안 성질을 문서에 적을 때는 반드시 실행해서 확인한다.
"이 검사가 X를 막는다"는 주장은 X를 실제로 넣어 보기 전까지 가설이다.
```

그리고 이번에는 **문서를 고치는 것으로 끝나지 않았다.** macOS가 경로 탈출을
막지 못한다는 것이 사실로 확인됐고, 그것은 I-16의 심층 방어에 난 구멍이다.
Windows 이식은 처음부터 막도록 짰고(§3.2), macOS 강화는 I-20 후보로 남겼다.

### 9b.4 같은 실수가 세 번째 — 이제 패턴이다

2026-08-05, `wire/json`을 옮기자 파리티가 두 줄을 뱉었다.

```text
Swift:  "irPath":"\/tmp\/x.ir.tiff"
C++:    "irPath":"/tmp/x.ir.tiff"
```

[encoding-and-json](../05-protocol/encoding-and-json.md) §2.3이 이렇게 적고
있었다.

> Swift `JSONEncoder`는 하지 않는다. Windows 구현도 하지 않아야
> 골든 파일 비교가 성립한다.

**반대였다.** Swift는 기본으로 `/`를 이스케이프하고, `.withoutEscapingSlashes`가
그것을 끄는 옵션이며, 제품 코드는 그 옵션을 켜지 않는다.

이것으로 파리티가 잡은 문서 오류가 셋이 됐다.

| 절 | 무엇을 틀렸나 | 공통점 |
|---|---|---|
| §9b | JSON 인코딩을 반대로 서술 | 실행하지 않고 적었다 |
| §9b.3 | 경로 검사가 정규화를 한다고 서술 | API 이름에서 추론했다 |
| §9b.4 | `/` 이스케이프를 반대로 서술 | 기본값을 추측했다 |

**셋 다 "라이브러리가 이렇게 할 것이다"였고 셋 다 틀렸다.** 그리고 셋 다
코드 한 줄 실행하면 30초에 확인되는 것이었다.

```text
런타임 동작을 문서에 적을 때는 그 API 를 실제로 호출해 본다.
"기본값이 X 다"는 특히 위험하다 — 그럴듯하고, 확인하기 쉽고, 아무도 안 한다.
```

### 9b.5 네 번째 — 이번에는 구현하기 전에 잡았다

2026-08-05, 요청 JSON 디코딩을 옮기기 전에
[encoding-and-json](../05-protocol/encoding-and-json.md) §6 을 읽었다. §6.4 가
이렇게 적고 있었다.

> Swift 구현이 무엇을 하는지는 확인 필요(대체로 마지막 값).

**반대였다. macOS 는 첫 값을 쓴다.**

```text
{"bitDepth":16,"bitDepth":8}   →  16
```

§9b~§9b.4 와 다른 점이 하나 있다. **이번에는 구현하기 전에 확인했다.**
그래서 파리티가 잡은 것이 아니라 실측이 잡았고, 잘못된 코드를 쓴 적이 없다.
"확인 필요"라고 적혀 있던 것이 컸다 — 앞의 셋은 단정문이라 의심받지 않았다.

같은 실측에서 문서에 없던 것도 열몇 개 나왔다(§6.5 표). 그중 셋은 구현을
바꿨다.

```text
Int 필드에 1200.5     타입 오류가 아니라 **문서 전체가 무효 JSON** 이다
필수 Bool 에 null      valueNotFound 가 아니라 typeMismatch 다
잘못된 UTF-8 바이트    거부하지 않는다. 그대로 통과한다
```

그리고 **라이브러리 쪽도 확인했다.** RapidJSON 1.1.0 의 수 변환이 macOS 와
갈린다 — `1e-324` 를 NaN 으로 만들고, `0e999` 를 "너무 크다"며 거부한다.
그래서 토큰화만 쓰고 수 변환은 `std::from_chars` 로 직접 한다.

```text
이식 대상만 실측하고 끝내지 않는다. **새로 붙이는 라이브러리도 같은 입력으로 재 본다.**
"검증된 라이브러리니까 표준대로 하겠지"가 §9b 계열과 같은 형태의 가정이다.
```

| 절 | 무엇을 틀렸나 | 언제 잡혔나 |
|---|---|---|
| §9b | JSON 인코딩을 반대로 서술 | 파리티 |
| §9b.3 | 경로 검사가 정규화를 한다고 서술 | 파리티 |
| §9b.4 | `/` 이스케이프를 반대로 서술 | 파리티 |
| §9b.5 | 중복 키를 마지막 값이라 서술 | **구현 전 실측** |

### 9b.6 다섯 번째 — 이번엔 **우리 문서**가 틀렸다

2026-08-05, MSVC 빌드를 준비하며 조사한 결과
[numerical-parity](../04-imaging/numerical-parity.md) §2.2 가 이렇게 적고
있었다.

> MSVC: /fp:precise (기본). /fp:fast를 쓰지 않는다.

그리고 그것을 믿고 `windows/CMakeLists.txt` 에도 주석이 달려 있었다.

```cmake
/fp:precise          # 기본이지만 명시한다. /fp:fast 는 절대 금지
```

**VS 2022 에서만 맞다.** VS 2019 이하에서 `/fp:precise` 의 기본
`fp_contract` 는 `on` 이고, **ARM64 에서는 스칼라 FMA 까지 낸다.**
`a + b*c` 가 한 명령이 되면 중간 반올림이 사라져 결과가 달라진다 — D-11 이
금지하는 바로 그것이다.

앞의 다섯과 다른 점이 둘이다.

```text
1. 틀린 것이 macOS 원본 서술이 아니라 **우리가 쓴 이식 문서**였다
2. 파리티가 못 잡는다. macOS 에서는 clang 이 -ffp-contract=off 로 옳게 돌기 때문이다
```

**두 번째가 무섭다.** 이 결함은 Windows 에서 처음 빌드하는 날까지 초록불로
있었을 것이고, 그날 터지는 것은 컴파일 오류가 아니라 **imaging 파리티의 1 ULP
차이**다. 원인이 코드에 없으니 한참 헤맸을 것이다.

이것은 §9b.2 와 같은 형태다. 그때는 파리티 스크립트가 실제 빌드보다 느슨했고,
이번엔 **한쪽 플랫폼에서만 옳은 플래그**였다.

```text
"기본값이 X 다"는 컴파일러 플래그에서도 위험하다.
**어느 버전, 어느 아키텍처의 기본값인지**까지 적지 않으면 절반만 맞는 문장이다.
```

고친 방법도 적어 둔다. 헤더 하나(`src/util/msvc_fp_contract.h`)를 CMake 가
`/FI` 로 **모든 번역 단위에 강제 포함**한다. "어느 파일이 부동소수점에
민감한가"를 사람이 판단하게 두면 언젠가 틀리고, 틀려도 빌드는 통과한다.

**왜 파리티가 이걸 계속 잡는가**: 이식자는 문서를 읽고 구현한다. 문서가
틀리면 구현도 틀린다. 단위 테스트는 그 틀린 이해를 그대로 고정할 뿐이다.
원본과 대조하는 것만이 문서와 무관하게 진실을 말한다.

핸드오프 §4.1이 "파리티 하네스가 이 작업의 핵심 도구다"라고 적은 이유가
이것이다. 지금까지 파리티가 잡은 것 중 **절반이 코드 버그가 아니라
문서 오류**다.

# 제2부 — 통한 것

## 10. 모델명이 아니라 옵션 덤프에서 감지한다

이 원칙 하나가 다른 어떤 결정보다 많은 문제를 예방했다.

**모델명은 하드웨어를 식별하지 못한다:**

| 함정 | 내용 |
|---|---|
| OpticFilm 8100 | `07b3:130c`는 genesys가 구동, `07b3:1824`는 **다른 Genesys 칩이라 어느 백엔드도 못 씀** |
| OpticFilm 8200i | `07b3:130d`는 구동, `07b3:1825`(GL128)는 미지원 |
| 8200i 자체 | **`-L`이 "OpticFilm 8100"으로 보고한다.** 우리 개발 장비가 그렇다 |
| epson2 | V800/V850을 `GT-X980`으로, V700/V750을 `GT-X900`으로 보고 |
| pieusb | USB ID **와** 모델 번호가 둘 다 맞아야 함 |

**모델명으로 분기했다면 개발 장비에서부터 틀렸을 것이다.**

지금 백엔드 **이름**으로 분기하는 곳은 문서화된 16곳뿐이고, 각각 upstream
소스나 실기 관측이 근거다. 모델명 분기는 0곳이다.

**Windows 함의**: 이식 중 새 분기를 추가하려면 (a) upstream 소스의 해당 줄
또는 (b) 실기 관측 기록이 있어야 한다. 이 규칙을 코드 리뷰 항목으로 만든다.

## 11. 순수 함수로 짜서 골든 픽스처가 가능해졌다

핵심 로직이 거의 전부 순수 함수다.

```text
SaneOptionDump(dump)                     문자열 → 구조
resolveMedia(dump, options, hint)        문자열 + 구조 → 구조
parseCapabilities(dump, hint, backend)   문자열 → 구조
validateExactOptions(options, media)     구조 → 통과/오류
makeScanimageArgs(dev, options, media)   구조 → 문자열 배열
epson2AlignedHeightMM(...)               수 → 수
containsExactly(...)                     수 → 불리언
mergeHardwareExposureBitmap(...)         픽셀 → 픽셀
estimateIntegerOffset(...)               픽셀 → 정수 쌍
```

**이것이 이식 프로젝트를 가능하게 만든 단일 요인이다.** 약 3,000행의
파싱·검증 로직이 플랫폼 의존 0이고, 골든 파일로 기계 검증할 수 있다.

플랫폼 의존이 실제로 박힌 곳은 셋뿐이다: 프로세스/신호, Core Image/ImageIO,
경로/환경변수.

**Windows 함의**: M1(계약 동결)에서 Windows 코드를 **한 줄도 쓰지 않는다.**
골든부터 만든다. → [conformance-fixtures](../05-protocol/conformance-fixtures.md)

## 12. 가상 `scanimage`가 실제 자식 프로세스로 돈다

`VirtualScanimageFixture.swift`(405행)는 mock 객체가 아니라 **진짜 실행되는
가짜 `scanimage`** 다. `-L`/`-f`/`-A` 텍스트와 TIFF를 실제로 낸다.

덕분에 프로세스 생성·파이프·취소·좀비 방지까지 테스트 안에서 검증된다.

**이식에서 가장 값싼 승리다.** 이 픽스처가 내는 텍스트는 실제 백엔드가
무엇을 출력하는지에 대한 저장소의 유일한 기계 판독 기록이다. 언어 중립
corpus로 뽑으면 Windows 구현이 같은 입력에 같은 판정을 내는지 즉시 비교된다.

**Windows에서도 같은 것을 만든다**: 가상 `scanimage.exe`(M3).

## 13. 합성 픽스처 + 수치 측정으로 검증한다

**실제 스캔 이미지를 테스트에 넣지 않는다.** 눈으로 결과를 보고 판단하지도
않는다. 합성 픽스처를 만들고 수치로 측정한다.

이유:

- 실제 이미지는 한 컷에 과적합을 부른다
- "좋아 보인다"는 회귀를 잡지 못한다
- 저장소가 커지고 개인 데이터가 섞인다

**Windows 함의**: `merge/`, `align/` 픽스처는 64×64 또는 128×128 합성
이미지로 모든 분기를 통과시킨다. 실기 덤프(`dumps/`)는 수집하되
**시리얼 번호와 사용자 경로를 커밋 전에 확인**한다.

## 14. 실패를 조용히 넘기지 않는 설계

```text
종료 코드 0만으로 성공하지 않는다
result 이벤트만으로도 성공하지 않는다
TIFF를 열어 크기·심도·색 모델을 확인한 뒤에만 result를 낸다
```

그리고 **정확한 옵션만 적용한다**: 가장 가까운 값으로 스냅하지 않고,
반올림 경고를 무시하지 않고, "거의 맞으니까 괜찮다"가 없다.

이 두 규칙이 "왜 스캔이 이상하지?"류 버그를 원천 차단했다. 실패는
**시작 전에** 또는 **결과 검증에서** 드러난다. 중간에 조용히 변질되지 않는다.

Mock이나 fallback 장치도 없다. 스캐너를 못 찾으면 못 찾은 것이다.

**Windows 함의**: 검증 13단계를 하나도 빼지 않는다. 오히려 늘린다
(D-10: SAMPLEFORMAT, PLANARCONFIG 추가).

## 15. 장치를 필요 이상으로 열지 않는다

전용 필름 스캐너는 **연속해서 여러 번 열면 다음 획득이 실패할 수 있다.**
실측(OpticFilm)에서 나온 사실이다.

그래서:

- `canReuseSinglePassOptionsDump` — 단일 투과 소스 genesys는 덤프 재사용
- `capabilityRedumpArguments` — 소스 때문에 어차피 다시 열 때 모드를
  **같은 호출에 함께 실어** 추가 open을 없앤다
- 정상 Color 경로에서 scan 전 장치 open **0회**

**이건 성능 최적화가 아니라 신뢰성 요건이다.** 최적화로 오해하고
"단순하게" 매번 새로 열도록 바꾸면 간헐적 스캔 실패가 돌아온다.

**Windows 함의**: 전송 계층이 바뀌어도(WinUSB, usbip) 이건 **장치 쪽
사실**이므로 그대로 유지한다.

## 16. 자기가 만든 프로세스만 다룬다

이름이나 경로로 전역 프로세스를 찾아 죽이지 않는다. 백엔드 인스턴스가
직접 생성해 보관한 `Process`만 취소 대상이다.

**사용자가 다른 SANE 프런트엔드를 동시에 쓰고 있을 수 있다.**

**Windows 함의**: Job Object를 쓰되 **우리가 만든 자식만** 담는다.
`taskkill /IM scanimage.exe` 같은 유혹을 코드 리뷰에서 막는다.

## 17. 패치된 런타임을 최우선 경로로 둔다

`scanimage` 탐색 순서에서 **패치된 keg를 최우선**으로 두고, 같은 keg의
`etc/sane.d`와 `lib/sane`을 **함께** 쓴다.

```text
NEGAFLOW_SCANIMAGE_PATH
/opt/homebrew/opt/sane-backends-negaflow/bin/scanimage   ← 패치본
/usr/local/opt/sane-backends-negaflow/bin/scanimage
/opt/homebrew/bin/scanimage                              ← stock
...
```

**stock 설정이 섞이면 Coolscan 패치가 우회된다.** 실행 파일만 패치본이고
설정/백엔드 라이브러리는 stock인 조합이 최악이다 — 동작하는 것처럼 보이다가
특정 기기에서만 터진다.

**Windows 함의**: keg 개념이 없으므로 **이 우선순위를 다시 설계해야 한다.**
번들 SANE를 쓰되 `NEGAFLOW_SCANIMAGE_PATH` 재정의는 유지하고(D-08),
사용자 지정 경로를 쓰면 **버전과 백엔드 구성이 우리 것과 다를 수 있음을
진단에 기록**한다. 설정 디렉터리도 실행 파일과 짝을 맞춰 고른다.

# 제3부 — 규칙으로 굳은 것

터진 사건들에서 나온 규칙을 한곳에 모은다. 각각은 위의 어떤 사고가 근거다.

| 규칙 | 근거 사건 |
|---|---|
| 실기 없이 하드웨어 동작 로직을 바꾸지 않는다 | §1 감마 리버트 |
| 구현 전에 manpage·릴리스 노트를 읽는다 | §2 노출 막다른 길 |
| 필요량과 가용량을 수치로 먼저 비교한다 | §2 |
| 패치된 SANE를 쓰고 적용 여부를 배포물마다 명시한다 | §3 word-list |
| 도달 불가 코드를 "연결"하지 않는다 | §4 cleanImage |
| GPL 경계는 CI로 강제한다 | §5 negadoctor |
| 측정과 소비의 색 도메인을 일치시킨다 | §6 base 랜덤 |
| 출력 TIFF에 ICC 프로파일을 넣지 않는다 | §6 |
| CI와 같은 플래그로 로컬 검사한다 | §7 |
| 테스트가 사용자 데이터에 닿지 않게 격리한다 | §8 |
| 최적화 전에 병목을 측정한다 | §9 |

| "라이브러리 기본값이 X"는 호출해 보고 적는다 | §9b.4 |
| 모델명으로 분기하지 않는다 | §10 |
| 이식은 개선의 기회가 아니다 (I-20) | §1 |

## 18. 이식자에게 하는 한 가지 부탁

이 문서에 있는 항목을 코드에서 마주치면, **고치기 전에 여기를 검색한다.**

특히 다음 다섯 개는 "명백히 개선할 수 있어 보이는데 실제로는 이미 시도돼
실패한 것"이다.

```text
1. epson2 --gamma-correction 활성 검사      (§1)
2. genesys 노출/밝기 옵션                    (§2)
3. IRStrategy.cleanImage 연결                (§4)
4. 노출 병합 SIMD 최적화                     (§9)
5. 장치를 매번 새로 여는 단순화              (§15)
```

다섯 개 전부 코드만 보면 "정리하면 좋겠다"로 보인다.

그리고 3번은 혼자가 아니다. **호출되지 않는 코드가 넷 있고 전부 연결하면
불변식을 깬다** — 목록은
[porting-map](../06-build/porting-map.md) §3.5에 있다.
